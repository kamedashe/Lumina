# Eval-харнес для поиска в Lumina

Измерение качества retrieval на размеченном наборе запросов к собственному
корпусу. Без фреймворков и без LLM-as-judge: всё детерминированно и
воспроизводится одной командой.

**Итог одним предложением.** На golden set из 54 размеченных запросов замена
англоцентричной модели эмбеддингов `nomic-embed-text` на мультиязычную
`bge-m3` подняла recall@5 с **0.167 до 0.600** на dev (+0.433, 95% бутстрэп
[+0.27, +0.60], улучшилось 14 запросов из 30, ухудшилось 0) и дала **0.714**
на отложенной выборке; по пути харнес нашёл в ретривере три дефекта, которых
не было видно без измерения, и отверг две мои собственные гипотезы о причинах.

---

## Что измеряется

Поиск, а не генерация. Метрики — recall@k, nDCG@k, MRR при бинарной
релевантности. Ни одного вызова LLM: прогон бесплатен и повторяется сколько
угодно раз.

## Корпус и разметка

19 файлов собственного проекта: `README.md`, `PLUGINS.md`, исходники на Rust
(`src-tauri/src/**`) и Python-сайдкар. 206 фрагментов при нарезке 1000/200,
509 при 400/80.

54 запроса, размеченных вручную одним человеком. Поле `kind`:

| kind | что это | доля |
|---|---|---|
| `verbatim` | вопрос сформулирован словами самого фрагмента | ~35% |
| `paraphrase` | вопрос сознательно другой лексикой | ~40% |
| `real` | настоящие запросы к Lumina: обрывочные, с опечатками | ~25% |

Плюс 10 негативов с пустым `relevant_spans` — вопросы, ответа на которые в
корпусе нет.

Разбиение **dev (37) / holdout (17)** сделано до любого тюнинга, со
стратификацией по `kind`. Holdout открыт **один раз**, в самом конце.

### Релевантность размечена цитатами, а не идентификаторами чанков

Строка набора выглядит так:

```json
{"id": "q014", "query": "что превращает неуспешный ответ в читаемую ошибку?",
 "relevant_spans": [{"path": "src-tauri/src/providers/sse.rs",
                     "quote": "/// Превращает неуспешный ответ в читаемую ошибку."}],
 "kind": "paraphrase"}
```

Цитата резолвится в символьный диапазон, хит считается релевантным при
**пересечении диапазонов**. Так сделано потому, что разметка списком
`chunk_id` умирает при первой же смене размера чанка: другие границы — другие
номера. Со спанами набор пережил четыре разных чанкинга без переразметки, и
размер чанка стал измеримой ручкой, а не константой.

Смещения считаются **в символах, а не в байтах** — на кириллице это разные
числа, и байтовые молча разъехались бы с питоновским `str.find()`.

## Результаты (dev, 30 позитивных запросов)

| конфигурация | чанк | модель | recall@1 | recall@5 | recall@10 | nDCG@10 | MRR |
|---|---|---|---|---|---|---|---|
| `chunk_1000` (базовая линия) | 1000/200 | nomic, без префиксов | 0.100 | 0.167 | 0.300 | 0.154 | 0.144 |
| `chunk_1000_prefix` | 1000/200 | nomic + префиксы | 0.133 | 0.300 | 0.333 | 0.200 | 0.184 |
| `chunk_250` | 250/50 | nomic, без префиксов | 0.067 | 0.170 | 0.210 | 0.129 | 0.121 |
| `chunk_250_prefix` | 250/50 | nomic + префиксы | 0.170 | 0.203 | 0.210 | 0.195 | 0.211 |
| `mxbai_400` (контроль) | 400/80 | mxbai-embed-large | 0.067 | 0.247 | 0.280 | 0.164 | 0.140 |
| `bge_m3` | 1000/200 | bge-m3 | 0.200 | 0.533 | 0.567 | 0.349 | 0.356 |
| **`bge_m3_400`** | 400/80 | bge-m3 | **0.450** | **0.600** | **0.633** | **0.547** | **0.537** |

Разрез по `kind`, recall@5 — он и объясняет, что происходит:

| конфигурация | verbatim | paraphrase | real |
|---|---|---|---|
| `chunk_1000` | 0.273 | 0.167 | 0.000 |
| `chunk_1000_prefix` | 0.545 | 0.167 | 0.143 |
| `mxbai_400` | 0.400 | 0.167 | 0.143 |
| `bge_m3_400` | 0.591 | 0.708 | 0.429 |

### Отложенная выборка

Один прогон `bge_m3_400`, 14 позитивных запросов:

| метрика | значение | 95% бутстрэп |
|---|---|---|
| recall@1 | 0.500 | [0.214, 0.786] |
| recall@5 | 0.714 | [0.500, 0.929] |
| recall@10 | 0.714 | [0.500, 0.929] |
| MRR | 0.578 | [0.345, 0.810] |

Holdout выше dev (0.714 против 0.600), но при 14 запросах интервалы
перекрываются полностью — это одна величина, а не улучшение.

### Попарные сравнения

Средние по 30 запросам легко обманывают, поэтому разница считается попарно по
каждому запросу, с бутстрэп-интервалом:

| сравнение | метрика | разница | 95% | лучше / хуже |
|---|---|---|---|---|
| `bge_m3_400` vs `chunk_1000` | recall@5 | +0.433 | [+0.267, +0.600] | 14 / 0 |
| `bge_m3_400` vs `chunk_1000` | recall@1 | +0.350 | [+0.183, +0.517] | 11 / 0 |
| `bge_m3_400` vs `mxbai_400` | recall@5 | +0.353 | [+0.140, +0.553] | 14 / 2 |
| `chunk_1000_prefix` vs `chunk_1000` | recall@5 | +0.133 | [+0.033, +0.267] | 4 / 0 |
| `bge_m3_400` vs `bge_m3` | recall@5 | +0.067 | [−0.033, +0.200] | 3 / 2 |

Последняя строка — пример того, ради чего интервалы и считаются: в таблице
средних видна прибавка, а интервал накрывает ноль, и заявлять эффект нельзя.

## Что харнес нашёл

**1. Два локальных бэкенда ранжировали по разным метрикам.** `sqlite`
считал косинус, `sqlite-vec` — L2 по ненормированным векторам (норма
`nomic-embed-text` ≈ 10, расстояния порядка 14). На одних данных это два
разных порядка. Исправлено нормализацией в одной точке — в `providers::embed`:
на единичных векторах порядок по L2 совпадает с порядком по косинусу.

**2. `nomic-embed-text` работал без обязательных task-префиксов.** Модель
обучена с асимметричными префиксами `search_document: ` и `search_query: `.
Включение подняло recall@5 с 0.167 до 0.300 при нуле регрессий. Теперь это
дефолт для моделей семейства nomic, переопределяемый через конфиг.

**3. Размер чанка задан в символах, а контекст модели — в токенах.**
Фрагмент в 1000 символов кириллицы не влезает в 512-токенный контекст
`mxbai-embed-large`: индексация падала с 500-й ошибкой, а сообщение при этом
советовало `ollama pull`, то есть указывало не на ту причину. Диагностика
исправлена, ограничение задокументировано.

## Что харнес опроверг

Обе гипотезы были моими собственными и обе звучали убедительно:

**«Виноваты ненормированные векторы».** После нормализации ранги не сдвинулись
ни на одну позицию: нормы у чанков оказались почти одинаковыми. Патч
правильный по другой причине (согласованность бэкендов), но заявленной
причиной низких метрик он не был.

**«Цитата занимает 6% чанка, надо резать мельче».** Чанк 250 против 1000 на
той же модели: recall@5 −0.097, 95% [−0.200, −0.013], ноль улучшений на
четыре ухудшения. Достоверно хуже.

Настоящей причиной оказался язык запросов. Разрез по языку на nomic:
recall@10 **0.280 на русских запросах против 0.600 на английских**. Контроль
`mxbai_400` (сильная английская модель, тот же чанк) дал 0.247 против 0.600
у мультиязычной `bge-m3` — то есть дело именно в языке, а не в «модель
получше».

## Ограничения

Читать вместе с цифрами, а не после них.

- **Один разметчик.** Второго мнения о релевантности нет, систематическая
  ошибка суждения не измерена.
- **Бинарная релевантность.** «Частично отвечает» не различается от «отвечает».
- **Один корпус, 19 файлов, преимущественно исходный код.** На корпусе прозы
  выводы могут быть другими.
- **Малые выборки.** 30 позитивов на dev, 14 на holdout, подгруппы по `kind` —
  от 3 до 16 запросов. Интервалы широкие, и это отражено в каждом сравнении.
- **В наборе осознанно оставлены шесть дефектных строк** («что в этом
  документе?», «что за строка?» — вопросы без локального ответа). Они
  обнаружены уже после открытия holdout, и удалять их значило бы править
  тестовый набор, увидев результат. Из-за них абсолютные числа занижены;
  сравнение конфигураций они не искажают, потому что одинаковы для всех.
- **Holdout потрачен.** Любая следующая конфигурация меряется только на dev,
  до сбора нового отложенного набора.
- **Померено качество ПОИСКА, не качество ответов.** Про генерацию здесь нет
  ни одной цифры.

## Воспроизведение

```bash
ollama pull bge-m3

python evals/index_corpus.py --config evals/configs/bge_m3_400.json
python evals/run_eval.py --golden evals/golden.dev.jsonl --config evals/configs/bge_m3_400.json

python evals/sweep.py --golden evals/golden.dev.jsonl          # все конфигурации разом
python evals/compare.py chunk_1000 bge_m3_400 --metric recall@5 # попарно, с бутстрэпом
python evals/diagnose.py selftest --config evals/configs/bge_m3_400.json
```

У каждой конфигурации свой индекс в `evals/index/<name>` — иначе прогоны
затирали бы друг друга. Каждый прогон пишет `results/<config>__<golden>.json`
с построчными метриками и `.trace.jsonl` с задержками и хешем конфига.

## Устройство

```
evals/
  golden.jsonl            размеченный набор
  golden.dev.jsonl        2/3, на нём подбирается конфигурация
  golden.holdout.jsonl    1/3, открыт один раз
  metrics.py              recall@k, nDCG@k, MRR по пересечению спанов
  run_eval.py             один прогон, результат + трасса
  sweep.py                несколько конфигураций и сводная таблица
  compare.py              попарное сравнение с бутстрэп-интервалом
  diagnose.py             самопроверка конвейера и разбор отдельного запроса
  annotate.py             интерактивная разметка
  golden_tool.py          валидация, аудит качества, разбиение
  index_corpus.py         индексация корпуса по конфигу
  configs/                конфигурации прогонов
  results/                результаты и трассы
```
